# Mastodon 速率限制、反滥用检测和登录安全机制配合分析

## 1. 概述

Mastodon 采用了多层安全防护机制，通过速率限制、反滥用检测和登录安全的紧密配合，构建了一个全面的安全体系。这些机制相互协作，从不同维度保护系统免受自动化攻击、垃圾信息和未授权访问的威胁。

## 2. 速率限制机制

### 2.1 系统级速率限制 (Rack::Attack)

**位置**: `config/initializers/rack_attack.rb`

Rack::Attack 提供了系统级的请求速率限制，主要包括：

#### 2.1.1 API 请求限制
- **已认证用户**: 1500 次/5 分钟 (`throttle_authenticated_api`)
- **按令牌限制**: 300 次/5 分钟 (`throttle_per_token_api`)
- **未认证请求**: 300 次/5 分钟 (`throttle_unauthenticated_api`)
- **分页请求**: 300 次/15 分钟 (已认证和未认证分别限制)

#### 2.1.2 特定操作限制
- **媒体上传**: 30 次/30 分钟 (`throttle_api_media`)
- **删除操作**: 30 次/30 分钟 (`throttle_api_delete`)
- **媒体代理**: 30 次/10 分钟 (`throttle_media_proxy`)

#### 2.1.3 账号相关限制
- **注册**: 5 次/30 分钟 (`throttle_api_sign_up`)
- **OAuth 应用注册**: 5 次/10 分钟 (`throttle_oauth_application_registrations/ip`)

#### 2.1.4 IP 处理策略
- IPv6 地址按 /64 子网分组限制
- IPv4 地址按单个 IP 限制
- 这有效防止了通过切换 IPv6 地址绕过限制的攻击

### 2.2 应用级速率限制 (RateLimiter)

**位置**: `app/lib/rate_limiter.rb` 和 `app/models/concerns/rate_limitable.rb`

应用级速率限制针对特定业务操作：

#### 2.2.1 操作类型限制
- **关注操作**: 400 次/24 小时
- **发布状态**: 300 次/3 小时
- **报告操作**: 400 次/24 小时

#### 2.2.2 实现机制
- 使用 Redis 存储计数
- 按用户 ID 和操作类型分组
- 支持回滚机制（事务失败时递减计数）
- 提供标准 HTTP 速率限制响应头

## 3. 反滥用检测机制

### 3.1 垃圾内容检测 (Antispam)

**位置**: `app/lib/antispam.rb`

#### 3.1.1 检测逻辑
反滥用检测系统通过以下维度识别垃圾内容：

1. **账号年龄豁免**: 注册超过 1 周的账号享有部分豁免
2. **文本匹配**: 检查内容是否包含已知垃圾文本
   - `antispam:spammy_texts`: 临时垃圾文本集合
   - `antispam:all_time_spammy_texts`: 永久垃圾文本集合
3. **社交关系检查**: 检测是否向未关注自己的用户发送消息
   - 如果回复或提及的账号没有关注发送者，则标记为可疑

#### 3.1.2 处理机制
- 检测到垃圾内容时，系统会静默丢弃 (`SilentlyDrop`)
- 自动生成系统报告，标记为垃圾内容类别
- 避免通知被骚扰的用户

### 3.2 注册反垃圾机制

**位置**: `app/controllers/concerns/auth/registration_spam_concern.rb` 和 `app/models/user.rb`

#### 3.2.1 蜜罐字段
User 模型中包含多个蜜罐字段：
- `registration_form_time`: 记录表单加载时间
- `website`: 隐藏字段，正常用户不会填写
- `confirm_password`: 隐藏的确认密码字段

#### 3.2.2 表单时间验证
- `RegistrationFormTimeValidator` 检查表单提交时间
- 过快提交（小于 3 秒）被视为自动化注册

## 4. 登录安全机制

### 4.1 登录速率限制

**位置**: `config/initializers/rack_attack.rb`

#### 4.1.1 多层限制
- **按 IP 限制**: 25 次尝试/5 分钟 (`throttle_login_attempts/ip`)
- **按邮箱限制**: 25 次尝试/1 小时 (`throttle_login_attempts/email`)

这种双重限制策略：
- 防止单个 IP 对多个账号进行暴力破解
- 防止对单个账号进行分布式暴力破解

### 4.2 可疑登录检测

**位置**: `app/lib/suspicious_sign_in_detector.rb`

#### 4.2.1 检测条件
登录被标记为可疑的条件：
1. **未启用双因素认证** (`sufficient_security_measures?`)
2. **非首次登录** (`freshly_signed_up?`)
3. **来自新 IP 地址** (`previously_seen_ip?`)

#### 4.2.2 IP 匹配策略
- IPv4: 使用 /16 子网掩码进行模糊匹配
- IPv6: 使用 /64 子网掩码进行模糊匹配
- 这种策略在安全性和用户体验之间取得平衡

### 4.3 双因素认证 (2FA)

**位置**: `app/controllers/concerns/auth/two_factor_authentication_concern.rb`

#### 4.3.1 支持的认证方式
1. **OTP (时间-based 一次性密码)**: 使用 TOTP 算法
2. **WebAuthn**: 支持硬件安全密钥

#### 4.3.2 2FA 尝试限制
- **位置**: `app/controllers/auth/sessions_controller.rb:6`
- **限制**: 每小时最多 10 次尝试
- **实现**: 使用 Redis 计数，键格式为 `2fa_auth_attempts:{user_id}:{hour}`

### 4.4 登录活动记录

**位置**: `app/models/login_activity.rb` 和 `app/controllers/auth/sessions_controller.rb`

#### 4.4.1 记录内容
每次登录尝试都记录：
- IP 地址
- User-Agent
- 认证方法 (密码/OTP/WebAuthn)
- 成功/失败状态
- 失败原因

#### 4.4.2 通知机制
- **可疑登录**: 发送邮件通知用户
- **2FA 失败**: 每小时最多发送一次通知邮件

### 5.1 登录流程安全配合详解

#### 5.1.1 完整执行流程

```
│                          登录请求进入 Rack 中间件层                            │
└─────────────────────────────────────────────────────────────────────────────┘
                                      │
                                      ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  Step 1: Rack::Attack IP 阻止检查 (blocklist)                                │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │ 触发保护: IpBlock.blocked?(req.remote_ip)                             │  │
│  │ 读取状态:                                                              │  │
│  │   - 数据库: ip_blocks 表 (查询 IP 是否在阻止列表中)                      │  │
│  │ 写入状态: 无                                                           │  │
│  │ 失败处理: 立即返回 403 Forbidden，中断整个请求流程                       │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────────┘
                                      │ 通过
                                      ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  Step 2: Rack::Attack 登录速率限制检查 (按 IP)                               │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │ 触发保护: throttle_login_attempts/ip                                   │  │
│  │  条件: POST 请求 && 路径匹配 /auth/sign_in                              │  │
│  │  限制: 25 次 / 5 分钟                                                  │  │
│  │ 读取状态:                                                              │  │
│  │   - Redis: rack::attack:throttle_login_attempts/ip:<masked_ip>:<bucket>│  │
│  │   - 计数器值 (当前已尝试次数)                                            │  │
│  │ 写入状态:                                                              │  │
│  │   - Redis: INCR 计数器 (仅在检查通过后递增)                              │  │
│  │   - 设置 TTL = 5 分钟                                                  │  │
│  │ 失败处理:                                                              │  │
│  │   - 调用 throttled_responder                                           │  │
│  │   - 返回 HTTP 429 Too Many Requests                                    │  │
│  │   - 响应头包含: X-RateLimit-Limit, X-RateLimit-Remaining(=0),           │  │
│  │                X-RateLimit-Reset                                       │  │
│  │   - 响应体: { error: "Too many requests" }                             │  │
│  │   - 中断请求，不再进入应用层                                             │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────────┘
                                      │ 通过
                                      ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  Step 3: Rack::Attack 登录速率限制检查 (按邮箱/用户)                          │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │ 触发保护: throttle_login_attempts/email                                │  │
│  │  条件: POST 请求 && 路径匹配 /auth/sign_in                              │  │
│  │  限制: 25 次 / 1 小时                                                  │  │
│  │ 标识键: session[:attempt_user_id] 或 params[:user][:email]             │  │
│  │ 读取状态:                                                              │  │
│  │   - Redis: rack::attack:throttle_login_attempts/email:<identifier>:<bucket>│  │
│  │   - Session: session[:attempt_user_id] (如果存在)                       │  │
│  │ 写入状态:                                                              │  │
│  │   - Redis: INCR 计数器                                                  │  │
│  │   - 设置 TTL = 1 小时                                                  │  │
│  │ 失败处理: 同 Step 2，返回 429                                           │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────────┘
                                      │ 通过
                                      ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                          请求进入应用层 (SessionsController)                  │
└─────────────────────────────────────────────────────────────────────────────┘
                                      │
                                      ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  Step 4: prepend_before_action :check_suspicious!                          │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │ 触发保护: SuspiciousSignInDetector (预检测，标记状态)                     │  │
│  │ 执行时机: 在任何认证逻辑之前                                             │  │
│  │ 读取状态:                                                              │  │
│  │   - 数据库: users 表 (查找用户)                                         │  │
│  │   - 数据库: user_ips 表 (查询用户历史 IP)                                │  │
│  │     查询: @user.ips.contained_by(masked_ip).exists?                    │  │
│  │   - 数据库: users.otp_required_for_login (检查 2FA 状态)                │  │
│  │   - 数据库: users.current_sign_in_at (检查是否首次登录)                  │  │
│  │ 写入状态:                                                              │  │
│  │   - 实例变量: @login_is_suspicious = true/false                        │  │
│  │   - 不立即中断，只是标记后续是否需要发送通知                              │  │
│  │ 检测逻辑:                                                              │  │
│  │   suspicious? = !otp_required? && !first_login? && !known_ip?          │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────────┘
                                      │
                                      ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  Step 5: prepend_before_action :authenticate_with_two_factor                │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │ 触发条件: two_factor_enabled? (用户启用了 2FA)                          │  │
│  │ 分支 A: 首次提交 (携带 email + password)                                │  │
│  │   ├─ 验证密码: user.external_or_valid_password?(password)              │  │
│  │   ├─ 读取状态: users.encrypted_password                                │  │
│  │   ├─ 验证通过 → prompt_for_two_factor(user)                            │  │
│  │   └─ 写入 Session:                                                     │  │
│  │       session[:attempt_user_id] = user.id                              │  │
│  │       session[:attempt_user_updated_at] = user.updated_at.to_s         │  │
│  │                                                                       │  │
│  │ 分支 B: 2FA 提交 (携带 otp_attempt 或 credential)                       │  │
│  │   ├─ 读取 Session: 验证 session[:attempt_user_updated_at] 未过期        │  │
│  │   ├─ 检查 2FA 速率限制: check_second_factor_rate_limits(user)          │  │
│  │   │   ├─ 读取 Redis: 2fa_auth_attempts:{user_id}:{hour}                │  │
│  │   │   ├─ 写入 Redis: INCR + EXPIRE 1.hour                              │  │
│  │   │   └─ 超过限制 (>=10次):                                            │  │
│  │   │       ├─ 提示: flash[:alert] = "Too many attempts"                 │  │
│  │   │       └─ 返回 2FA 页面，不记录失败活动                               │  │
│  │   ├─ 验证 2FA 凭据:                                                    │  │
│  │   │   ├─ OTP: valid_otp_attempt?(user)                                │  │
│  │   │   │   └─ 读取/更新: users.consumed_timestep                        │  │
│  │   │   └─ WebAuthn: valid_webauthn_credential?(user, credential)        │  │
│  │   │       └─ 更新: webauthn_credentials.sign_count                     │  │
│  │   └─ 验证失败:                                                         │  │
│  │       ├─ on_authentication_failure(user, :otp/:webauthn, reason)       │  │
│  │       ├─ 写入数据库: login_activities (success: false)                 │  │
│  │       ├─ 检查 Redis: 2fa_failure_notification:{user_id} (1小时锁)       │  │
│  │       └─ 发送邮件: UserMailer.failed_2fa (限频)                         │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────────┘
                                      │ 2FA 验证通过 或 未启用 2FA
                                      ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  Step 6: 密码验证 (Devise 标准流程)                                          │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │ 触发: Devise::SessionsController#create                                │  │
│  │ 读取状态:                                                              │  │
│  │   - 数据库: users.encrypted_password                                   │  │
│  │ 验证失败处理:                                                           │  │
│  │   - Devise 默认行为: 返回登录页面 + 错误消息                             │  │
│  │   - 注意: 此时 Rack::Attack 计数器已递增                                │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────────┘
                                      │ 验证通过
                                      ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  Step 7: on_authentication_success (登录成功后处理)                          │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │ 清理状态:                                                              │  │
│  │   - Redis: DEL 2fa_auth_attempts:{user_id}:{hour}                      │  │
│  │   - Session: 删除 :attempt_user_id, :attempt_user_updated_at           │  │
│  │                                                                       │  │
│  │ 更新用户状态:                                                          │  │
│  │   - 数据库: user.update_sign_in!(new_sign_in: true)                    │  │
│  │     ├─ 递增 sign_in_count                                              │  │
│  │     ├─ 更新 last_sign_in_at = current_sign_in_at                       │  │
│  │     └─ 更新 current_sign_in_at = Time.now                              │  │
│  │                                                                       │  │
│  │ 写入共享状态:                                                          │  │
│  │   - 数据库: login_activities.create!                                   │  │
│  │     ├─ ip: request.remote_ip                                          │  │
│  │     ├─ user_agent: request.user_agent                                 │  │
│  │     ├─ authentication_method: :password/:otp/:webauthn                │  │
│  │     └─ success: true                                                  │  │
│  │                                                                       │  │
│  │   - 数据库: user_ips (通过 update_sign_in! 间接更新)                    │  │
│  │     └─ 记录当前 IP，供后续可疑登录检测使用                                │  │
│  │                                                                       │  │
│  │ 可疑登录通知:                                                          │  │
│  │   - 如果 @login_is_suspicious == true:                                 │  │
│  │     └─ UserMailer.suspicious_sign_in.deliver_later!                   │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 5.1.2 登录流程共享状态汇总表

| 步骤 | 操作 | 读取的共享状态 | 写入的共享状态 | 中断条件 |
|-----|------|--------------|---------------|---------|
| Step 1 | IP 阻止检查 | `ip_blocks` 表 | 无 | IP 在阻止列表中 → 403 |
| Step 2 | IP 登录速率限制 | Redis: `rack::attack:throttle_login_attempts/ip:*` | Redis: INCR 计数器 + TTL | 计数 >= 25 → 429 |
| Step 3 | 邮箱登录速率限制 | Redis: `rack::attack:throttle_login_attempts/email:*`, Session | Redis: INCR 计数器 + TTL | 计数 >= 25 → 429 |
| Step 4 | 可疑登录预检测 | `users` 表, `user_ips` 表 | `@login_is_suspicious` (内存) | 从不中断，仅标记 |
| Step 5 | 2FA 验证 | Session, Redis: `2fa_auth_attempts:*`, `users` 表, `webauthn_credentials` 表 | Session, Redis: INCR 计数器, `login_activities` (失败时) | 2FA 失败 → 返回 2FA 页面 |
| Step 6 | 密码验证 | `users.encrypted_password` | 无 | 密码错误 → 返回登录页 |
| Step 7 | 成功后处理 | 无 | Redis: DEL 2FA 计数, `login_activities`, `user_ips`, `users.sign_in_*` | 从不中断 |

#### 5.2.2 发帖流程共享状态汇总表

| 步骤 | 操作 | 读取的共享状态 | 写入的共享状态 | 中断条件 |
|-----|------|--------------|---------------|---------|
| Step 1 | IP 阻止检查 | `ip_blocks` 表 | 无 | IP 被阻止 → 403 |
| Step 2 | 用户 API 速率限制 | Redis: `rack::attack:throttle_authenticated_api:*` | Redis: INCR 计数器 | 计数 >= 1500 → 429 |
| Step 3 | 令牌 API 速率限制 | Redis: `rack::attack:throttle_per_token_api:*` | Redis: INCR 计数器 | 计数 >= 300 → 429 |
| Step 4 | 权限检查 | `users`, `accounts`, `oauth_access_tokens` | 无 | 认证失败 → 401/403 |
| Step 5 | 幂等性检查 | Redis: `idempotency:status:*`, `idempotency:lock:*` | Redis: SETEX (记录幂等键) | 重复请求 → 返回缓存结果 |
| Step 6 | 媒体验证 | `media_attachments` 表 | 无 | 验证失败 → 422 |
| Step 7 | 反垃圾检测 | Redis: `antispam:*_spammy_texts`, `accounts`, `follows` | `reports` 表 (垃圾时) | 检测为垃圾 → 静默丢弃 |
| Step 8 | 应用级速率限制 | Redis: `rate_limit:<account_id>:statuses:*` | Redis: INCR/DECR, `statuses` 表 | 超限 → 事务回滚 + 异常 |
| Step 9 | 后续处理 | 无 | `tags`, Redis trends, 异步任务 | 从不中断 |

| Step 6 | 构建 User | Session: `registration_form_time` | User 对象属性 | 从不中断 |
| Step 7 | 模型验证 | DNS MX 记录, 域名黑白名单配置, `invites` 表 | 无 | 任意验证失败 → 返回错误 |
| Step 8 | 保存用户 | 无 | `users`, `accounts`, `invites.uses`, 异步任务 | 从不中断 |

## 6. 多重限制同时命中的执行顺序与返回结果

### 6.1 Rack::Attack 限制的执行顺序

**位置**: `config/initializers/rack_attack.rb`

Rack::Attack 按照规则在代码中定义的顺序依次检查。以下是关键规则的定义顺序及其优先级：

```
执行顺序 (高 → 低):
1. blocklist('deny from blocklist')           ← 最先执行，IP 阻止
2. throttle('throttle_authenticated_api')     ← 已认证 API
3. throttle('throttle_per_token_api')         ← 按令牌 API
4. throttle('throttle_unauthenticated_api')   ← 未认证 API
5. throttle('throttle_api_media')             ← 媒体上传
6. throttle('throttle_media_proxy')           ← 媒体代理
7. throttle('throttle_api_sign_up')           ← API 注册
8. throttle('throttle_authenticated_paging')  ← 已认证分页
9. throttle('throttle_unauthenticated_paging')← 未认证分页
10. throttle('throttle_api_delete')           ← 删除操作
11. throttle('throttle_oauth_application_registrations/ip')
12. throttle('throttle_sign_up_attempts/ip')  ← Web 注册
13. throttle('throttle_password_resets/ip')
14. throttle('throttle_password_resets/email')
15. throttle('throttle_email_confirmations/ip')
16. throttle('throttle_email_confirmations/email')
17. throttle('throttle_auth_setup/email')
18. throttle('throttle_auth_setup/account')
19. throttle('throttle_login_attempts/ip')    ← 登录 (按 IP)
20. throttle('throttle_login_attempts/email') ← 登录 (按邮箱)
21. throttle('throttle_password_change/account')
```

### 6.2 多重限制命中的处理规则

#### 6.2.1 短路原则

Rack::Attack 采用**短路求值**策略：
- **第一个匹配到的限制规则**会立即生效
- **后续规则不再检查**
- 返回第一个命中规则的限制参数

#### 6.2.2 典型场景分析

**场景 1: 登录请求同时命中多个限制**

假设攻击者：
- 来自已被阻止的 IP
- 同时超过了 IP 登录限制 (25/5min)
- 也超过了邮箱登录限制 (25/1h)

**执行流程**:
```
请求 → Step 1: blocklist 检查 → 命中!
            │
            └─ 立即返回 403 Forbidden
               (不检查后续 throttle_login_attempts 规则)
```

**结果**: 返回 403，而不是 429

---

**场景 2: 登录请求同时命中 IP 和邮箱限制**

假设：
- IP 计数 = 25 (已超限)
- 邮箱计数 = 25 (已超限)

**执行流程**:
```
请求 → Step 1: blocklist → 未命中
     → Step 2: throttle_login_attempts/ip → 命中! (计数 25 >= 25)
            │
            └─ 立即返回 429
               响应头使用 IP 限制的参数:
               - X-RateLimit-Limit: 25
               - X-RateLimit-Reset: 5 分钟后
               (不检查 throttle_login_attempts/email)
```

**结果**: 返回 429，使用**先命中**的 IP 限制参数

---

**场景 3: 发帖请求同时命中多层 API 限制**

假设用户：
- 用户 API 计数 = 1500 (已超限，5 分钟窗口)
- 令牌 API 计数 = 300 (已超限，5 分钟窗口)
- 应用级发帖计数 = 300 (已超限，3 小时窗口)

**执行流程**:
```
请求 → Rack 层:
       Step 1: blocklist → 未命中
       Step 2: throttle_authenticated_api → 命中! (1500 >= 1500)
              │
              └─ 立即返回 429
                 (不检查 throttle_per_token_api)
                 (不进入应用层)
                 (不触发 RateLimiter)
```

**结果**: 
- 返回 429，使用 `throttle_authenticated_api` 的参数 (Limit: 1500)
- **应用级 RateLimiter 不会被触发**
- **Redis 应用级计数器不会递增**

---

**场景 4: 发帖仅命中应用级限制**

假设：
- Rack::Attack 所有 API 限制都未命中 (剩余配额充足)
- 但应用级 `rate_limit:statuses` 计数 = 300 (已超限)

**执行流程**:
```
请求 → Rack 层所有检查通过
     → 进入应用层 → PostStatusService
     → Status.save! → after_create 回调
     → RateLimiter.record!
        │
        ├─ 读取 Redis: rate_limit:{user_id}:statuses:{bucket} = 300
        ├─ 检查: 300 >= 300? → 是
        │
        └─ 抛出 Mastodon::RateLimitExceededError
           → 事务回滚
           → after_rollback: RateLimiter.rollback! (DECR Redis)
           → API 控制器捕获异常 → 返回 429
```

**结果**:
- 返回 429 (由应用层生成，不是 Rack::Attack)
- **注意**: 没有标准的 X-RateLimit-* 响应头
- Redis 计数先 INCR 再 DECR (净变化为 0)

---

**场景 5: 发帖同时命中反垃圾和应用级限制**

假设：
- Rack 层检查通过
- 内容被 Antispam 检测为垃圾
- 同时应用级速率也超限

**执行流程**:
```
请求 → Rack 层通过
     → PostStatusService#process_status!
        │
        ├─ 步骤 1: Antispam.local_preflight_check!
        │      │
        │      └─ 检测到垃圾 → 抛出 SilentlyDrop
        │         (在 Status.save! 之前执行)
        │
        └─ 步骤 2: 不会执行 Status.save!
              所以 RateLimiter 永远不会被触发
```

**结果**:
- 静默丢弃，返回 DummyStatus
- **应用级 RateLimiter 计数不会递增**
- **自动创建系统 Report**

---

### 6.3 多层限制的优先级总表

| 层级 | 机制 | 执行时机 | 优先级 | 失败返回 | 是否递增计数器 |
|-----|------|---------|-------|---------|--------------|
| L1 | Rack::Attack blocklist | 请求最开始 | 最高 (1) | 403 | 否 |
| L2 | Rack::Attack throttle | 请求进入应用前 | 高 (2) | 429 + 标准头 | 是 (命中前已递增) |
| L3 | 应用权限/认证 | 控制器 before_action | 中 (3) | 401/403 | 否 |
| L4 | Antispam 检测 | Service 业务逻辑中 | 中 (4) | 静默丢弃 | 否 |
| L5 | RateLimiter 应用级 | Model after_create | 低 (5) | 429 (无标准头) | 是 (后回滚) |
| L6 | 2FA 应用级限制 | 控制器逻辑中 | 低 (6) | 页面提示/422 | 是 (Redis) |

### 6.4 计数器递增的关键注意事项

#### 6.4.1 Rack::Attack 计数器行为

**计数器递增时机**: 在**检查之后**、**响应之前**

```ruby
# Rack::Attack 内部逻辑 (简化)
def matches_throttle?(req)
  discriminator = yield(req)
  return false if discriminator.nil?
  
  key = "#{name}:#{discriminator}:#{bucket}"
  count = redis.get(key) || 0
  
  # 先检查
  if count >= limit
    return true  # 命中，返回 true
  end
  
  # 检查通过后才递增
  redis.incr(key)
  redis.expire(key, period)
  return false
end
```

**关键点**:
- 命中限制时，**计数器不再递增**（已经达到上限）
- 未命中时，**计数器递增 1**
- 验证失败（如密码错误）但未超限 → **计数器会递增**

#### 6.4.2 RateLimiter 应用级计数器行为

```ruby
# app/models/concerns/rate_limitable.rb
after_create do
  if rate_limit? && by&.local?
    rate_limiter(by, options).record!  # 可能抛出异常
    @rate_limit_recorded = true
  end
end

after_rollback do
  if @rate_limit_recorded
    rate_limiter(...).rollback!  # DECR Redis
  end
end
```

**关键点**:
- `record!` 内部: 先 GET → 检查 → 再 INCR
- 如果超限抛出异常 → **不执行 INCR**
- 如果 INCR 后其他原因导致回滚 → 执行 DECR (净变化 0)
- 正常成功 → 净变化 +1

#### 6.4.3 验证失败对计数器的影响

| 场景 | Rack::Attack 计数 | 应用级 RateLimiter 计数 |
|-----|------------------|----------------------|
| 登录密码错误 (未超限) | +1 | 不涉及 |
| 登录密码错误 (已超限) | 不变 (已达上限) | 不涉及 |
| 注册邮箱验证失败 | +1 | 不涉及 |
| 发帖媒体验证失败 | +1 (Rack API 限制) | 不变 (save 未执行) |
| 发帖被反垃圾检测命中 | +1 (Rack API 限制) | 不变 (save 未执行) |
| 发帖应用级超限 | +1 (Rack API 限制) | 先 +1 后 -1 (净 0) |

## 7. 关键技术实现细节

### 7.1 Redis 的核心作用

Redis 在整个安全体系中扮演着关键角色：

1. **速率限制计数**: 存储各类操作的计数和过期时间
2. **2FA 尝试记录**: 跟踪双因素认证尝试次数
3. **垃圾文本集合**: 维护已知垃圾内容的模式
4. **通知频率控制**: 防止邮件风暴
5. **幂等性控制**: 防止重复发帖
6. **会话状态**: 存储注册表单时间、规则接受令牌等

### 7.2 IP 地址处理策略

系统采用了精细化的 IP 处理策略：

- **速率限制 (Rack::Attack)**: IPv6 按 /64 子网，IPv4 按单个 IP
- **可疑登录检测**: IPv4 按 /16 子网，IPv6 按 /64 子网
- **IP 阻止**: 支持 CIDR 格式的 IP 段阻止

### 7.3 用户体验与安全的平衡

系统在安全性和用户体验之间取得平衡：

1. **子网模糊匹配**: 避免因动态 IP 导致的频繁可疑登录警告
2. **账号年龄豁免**: 老用户享有一定的反垃圾检测豁免
3. **渐进式限制**: 先警告，再限制，最后阻止
4. **详细的 HTTP 头**: 告知客户端剩余限额和重置时间
5. **静默丢弃**: 垃圾内容不通知被骚扰用户，同时不提示攻击者

## 8. 安全机制协同效应

### 8.1 多层防御体系

| 防御层次 | 主要机制 | 防护目标 | 失败返回 |
|---------|---------|---------|---------|
| 网络层 | Rack::Attack IP 阻止 | 阻止已知恶意 IP | 403 |
| 网络层 | Rack::Attack 速率限制 | 阻止大规模自动化攻击 | 429 |
| 应用层 | 权限/认证检查 | 确保操作授权 | 401/403 |
| 内容层 | Antispam 检测 | 过滤垃圾信息 | 静默丢弃 |
| 应用层 | RateLimiter 操作限制 | 防止滥用特定功能 | 429 |
| 账号层 | 2FA + 可疑登录检测 | 保护账号安全 | 页面提示/邮件 |
| 行为层 | 登录活动记录 + 通知 | 异常行为告警 | 无直接返回 |

### 8.2 信息共享机制

各安全机制之间通过以下方式共享信息：

1. **IP 历史记录**: `UserIp` 模型记录用户历史 IP，供可疑登录检测使用
2. **登录活动**: `LoginActivity` 记录所有登录尝试，可用于模式分析
3. **系统报告**: 反滥用检测生成的 `Report` 记录可供人工审核
4. **Redis 数据**: 跨模块共享速率限制计数、幂等键、通知频率锁等
5. **Session**: 注册表单时间、2FA 尝试状态、规则接受令牌等

## 9. 总结

Mastodon 的安全体系是一个设计精良的多层防御系统：

1. **速率限制**从源头上控制请求频率，防止资源耗尽和暴力破解
2. **反滥用检测**通过内容分析和行为模式识别垃圾信息
3. **登录安全**通过多因素认证和异常检测保护用户账号

这些机制通过**严格的执行顺序**和**短路原则**协同工作：
- **Rack 层优先**: 低成本的中间件检查先于昂贵的应用层逻辑
- **先阻止后限流**: IP 黑名单检查在所有速率限制之前
- **先检测后限流**: 反垃圾检测在应用级速率限制之前（避免浪费配额）
- **计数器递增策略**: 验证失败会消耗 Rack 层配额，但应用层异常会回滚

关键设计决策：
- **Rack::Attack 短路**: 第一个命中的规则立即返回，避免不必要的检查
- **应用级回滚机制**: RateLimiter 使用 after_rollback 确保计数一致性
- **静默丢弃策略**: 反垃圾检测不暴露检测结果给攻击者
- **限频通知**: 失败邮件通知有 Redis 锁防止邮件风暴

这种纵深防御策略确保了即使某一层被突破，其他层次仍然能够提供保护，同时通过精细的状态管理保证了安全机制的准确性和可靠性。
